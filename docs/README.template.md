# NoteRecall

Ask questions about your own Jupyter notebooks and get answers that cite the notebook cells they come
from, or a clear "not in your notes". See `PLAN.md` for the architecture and `CLAUDE.md` for contributor
rules. This README is generated by `scripts/render_readme.py` from `docs/README.template.md` and the files
in `results/`; every number below is read from those files.

## What the MVP does

Grounded question answering over a private notebook collection:

- **Retrieval.** BM25 over code-aware tokens plus a dense model (`BAAI/bge-base-en-v1.5`), fused with
  reciprocal rank fusion; every chunk is indexed with its notebook and heading path (ADR-004 to ADR-007).
- **Answer.** One `gpt-5-mini` call answers from the retrieved chunks only. Every claim must cite chunk
  ids that were in the context; invalid citations are retried once and then refused (ADR-011). Abstention
  rests on the model's own "insufficient" flag.
- **Conversation.** The last 5 turns are kept in the browser session. With history, one small model call
  rewrites a follow-up into a standalone question; the history is never evidence and no rewrite call is
  made without history.
- **Service.** A FastAPI service (`POST /ask`, `GET /health`, `GET /topics` for the notebook titles) and a
  Streamlit chat page ("ReRAG"), deployed as two
  free Render services. Limit: 15 questions per end-user IP per UTC day.

Deferred, not built: concept extraction, flashcards and the faithfulness judge (M7, ADR-012/013), FSRS
scheduling and the daily planner (M8, ADR-014). See `docs/proposals/009-mvp-grounded-qa-service.md`.

## Run it locally

```bash
make setup                       # uv sync --locked
uv run noterecall sync           # notebooks -> database (needs data/rerag-data)
uv run noterecall quantize-onnx  # fp32 ONNX model -> int8 model in data/artifacts/onnx-int8
uv run noterecall build-index    # chunks + int8 ONNX vectors -> data/artifacts
export OPENAI_API_KEY=...        # never committed, never logged
export UI_API_SECRET=local-secret
uv run uvicorn noterecall.api:build_app --factory --port 8000
# in a second terminal:
export API_URL=http://localhost:8000 UI_API_SECRET=local-secret
uv run streamlit run app/streamlit_app.py
```

## Mutation testing

`make mutation` changes the core code one site at a time (comparison swapped, `+`/`-`, `and`/`or`, an
integer moved by one, a boolean flipped, a `not` dropped) and runs the module's tests
(`scripts/mutation.py`, `results/mutation.json`). A mutant is killed if a test fails.

{{block:mutation}}

The survivor in `ratelimit.py` is an equivalent change, not a missing test: it moves the end of the
day by one microsecond, and the remaining time is truncated to whole seconds, so no result differs.
mutmut (pinned in the dev group) could not be used; see the docstring of `scripts/mutation.py`.

## Known limitations

- **Quantized dense model.** The served embeddings come from an int8 model, chosen because the fp32 one did
  not fit in 512 MB. Dev Recall@10 is lower than torch's by a small amount and the interval includes 0;
  the test split was not run for it, so the test-split retrieval table above is the torch model's.
- **Truncation.** At chunk cap 512, a share of chunks is longer than the dense model's input limit and is
  cut, so dense retrieval does not see their tails (counts in the earlier-milestones notes below, from
  `results/retrieval_ablation_dev.json`).
- **Abstention is weak.** Test split: {{block:test_refused_unanswerable}} unanswerable queries refused, with
  3 such queries, so the number is coarse. Stage-1 abstention refuses nothing on this corpus; the model's
  own flag does all the work.
- **Faithfulness is not measured.** The citation check is structural: a cited chunk exists and was in the
  context. It does not check that the chunk supports the claim. Known cases: q033 (an answer covering one
  side of a comparison was given for an unanswerable query) and q081 claim 1 (a cited chunk that does not
  support it). The judge that would catch these (M7) is deferred.
- **The public API exposes note content.** Every answer returns the cited chunks' text and there is no
  authentication; the only protection is the rate limit. Anyone with the URL can read parts of the notes.
- **Rate limit.** In memory, per API instance: it resets when the service restarts or redeploys. A visitor
  who changes IP address gets a fresh allowance, which also spends the owner's OpenAI budget.
- **Cold starts.** Free instances sleep when idle; the first request after that waits about a minute and
  the page says so.
- **Shared free hours.** Both services draw on the same 750 monthly free instance hours.
- **Not verified here:** the Render build itself (build secrets, memory), Render's proxy headers, and the
  Streamlit page in a real browser behind Render's proxy. They are tested with fakes and locally.

## Notes from earlier milestones

### Not tested (owner decision)

The LLM contextual blurb (ADR-007) and the LLM markdown clean (ADR-003) were **not tested**. They are
not run and ship off. This is the owner's decision on cost and benefit, recorded in
`docs/proposals/005-skip-llm-preprocessing.md`; it is not a result, and nothing here says they do or do
not help.

### Context header (M5, dev split)

The deterministic header (`{notebook} > {headings}` in front of each indexed chunk) is on, as ADR-007
requires. Its on/off row on the dev split, rendered from `results/header_ablation_dev.json` by
`scripts/render_results.py`:

| Configuration | Recall@5 | Recall@10 | MRR@10 | nDCG@10 |
|---|---|---|---|---|
| M4 pipeline, header off | 0.670 | 0.819 | 0.613 | 0.584 |
| M4 pipeline, header on | 0.713 | 0.860 | 0.672 | 0.647 |

Recall@10 difference +0.042, 95% CI [-0.029, +0.117] (paired bootstrap, 54 dev queries). The interval
includes 0, so this dev run does not establish a gain; the row is reported, not decided on. The header
also lengthens the indexed text: 344 of 2310 chunks are cut at the dense model's input limit with it, 294
without.

### Grounded Q&A (M6, dev split)

`noterecall ask "<question>"` answers from your notes with numbered sources, or says it is not in them.
Every claim must cite note IDs that were in the context; the validator rejects unknown IDs, claims with no
citation and empty answers, retries once with the problems listed, and otherwise refuses (ADR-011). The
validator checks structure only: whether a cited note really supports the claim is not measured yet (M7).

**Stage 1 abstention refuses nothing on this corpus.** Proposal 006 pre-registered a rule: refuse without
calling the model only if the top dense cosine and the normalized top BM25 score are both below thresholds
chosen on dev, subject to refusing at most 5% of the answerable queries. On the dev split no threshold pair
catches any of the 6 unanswerable queries within that bound (`results/abstention_calibration_dev.json`;
catching one needs at least 5 false refusals out of 54). In a single-domain corpus, unanswerable queries
that are near the topic of the notes look like answerable ones to cosine and to BM25. The selected
thresholds therefore refuse nothing, the bound was kept, and **abstention rests on the model's own
`insufficient` flag**. The ADR-011 Result line records this.

One answer-prompt revision was tried on dev under a rule written down first (proposal 006, addendum 1):
adopt it only if answerable queries refused stay at most 2/54 and unanswerable queries refused strictly
improve on 2/6. It met both, so the shipped prompt is the revision (it says to answer only if the notes
directly contain the answer). Both prompts side by side, rendered from `results/generation_dev.json`
(original) and `results/generation_dev_prompt2.json` (shipped) by `scripts/render_results.py`:

| Measure | original `f715ca2be4cf` | shipped `ee9346d6e271` |
|---|---|---|
| answerable queries refused | 0/54 | 0/54 |
| unanswerable queries refused | 2/6 | 3/6 |
| first attempt valid | 60/60 | 60/60 |
| retried | 0/60 | 0/60 |
| uncited claims, first attempt | 0/205 | 0/169 |
| gold-hit (answered answerable citing a gold chunk) | 45/54 | 45/54 |
| claims in all answers, first attempt | 205 | 169 |
| input / output tokens | 119804 / 12386 | 120344 / 11080 |
| cost USD | 0.0547 | 0.0522 |

The improvement is one unanswerable query out of six, so it is a pre-registered choice and not statistical
evidence; the revision also gives shorter answers (fewer claims). The other 3 unanswerable dev queries
are still answered, with citations that pass the structural check. Whether those answers are supported by
the cited notes is not measured yet (M7). Gold-hit says that 9 of the 54 answered answerable queries cite
no gold-labelled cell, which does not by itself make an answer wrong.

Test split (run once, `results/generation_test_M6.json`): answerable queries refused 0/22; unanswerable
queries refused 2/3 in both views (as labelled and adjudicated); first-attempt citation validity 25/25.
The one unanswerable query that was answered (q033) was adjudicated by the owner as a genuine abstention
miss, not a label error (proposal 006, addendum 3): its answer covers only one side of a comparison.
Abstention numbers are reported two ways, as labelled and adjudicated (owner-confirmed label errors, listed
by id in `config/default.toml`, left out); the gold file itself is unchanged. With 3 unanswerable test
queries the counts are coarse.

**The report-only abstention set was not built.** Proposal 007 planned a separate set of about 40 queries
for reporting abstention on more examples. The owner decided not to write it, so there is no result for it.
Its tooling (`label --id-prefix`, `gold validate --kind abstention`, `eval --suite generation --set
abstention`) exists and is tested but has never been run on real data.

### Post-answer verification (stage 3): tested on dev, not adopted

Proposal 007 added a third abstention stage: for each answered query, a second `gpt-5-mini` call at
reasoning effort `medium` received the question, the claims and the full text of the cited chunks, and
judged whether the cited notes directly answer the question and whether each claim is supported. It was
adopted only if answerable false refusals stayed at most 2/54 and unanswerable refusals strictly improved
on 3/6. On dev (results in `results/generation_dev_stage3.json`; the code that produced them is at commit
`4e877d8`):

| Measure | without stage 3 | with stage 3 |
|---|---|---|
| answerable queries refused | 0/54 | 0/54 |
| unanswerable queries refused | 3/6 | 3/6 |
| answered answerable queries citing a gold chunk | 45/54 | 44/54 |
| claims shown | 169 | 161 |
| model cost per query (USD) | 0.00087 | 0.00262 |
| median / 95th percentile model latency of an answered query (s) | 2.44 / 4.33 | 9.07 / 22.63 |

The rule was not met, so stage 3 was **not adopted and its code was removed** (it stays in git history).
The verifier judged "the cited notes answer the question" to be true for all 57 answered queries,
including the three unanswerable queries that are still answered; it dropped 8 of 169 claims and never
refused an answer. Cost per query was about 3 times higher and latency about 4 times (median). This is a
measurement on 6 unanswerable queries with the same model as the verifier; it was not run on the test
split. Abstention therefore still rests on the model's own `insufficient` flag.
