### ADR-004 — Structure-aware chunking on cell boundaries (amended by proposal 002)
A chunk = a markdown heading section and its following cells, split on **cell boundaries** when over the token cap. A single oversized cell is split at its natural units (amended by proposal 002): one top-level statement is the smallest unit of code, and markdown is split at paragraphs, then sentences; a fenced code block inside a markdown cell is never split. A chunk may exceed the cap only if it is a single indivisible unit, and it is then flagged. Code and the markdown that explains it stay together. Code cells are never split mid-statement. Cell outputs are excluded from chunk text by default and kept in the database; whether to include none, all, or only "evidence" outputs is an M4 ablation (proposal 002).
*Evidence:* Chroma's chunking study found splitter choice moves recall by several points and that simple structure-respecting splitters are competitive with LLM-based ones; a 2026 taxonomy paper (arXiv 2602.16974) found simple structure-based methods beat LLM-guided chunking for in-corpus retrieval. Notebooks have explicit structure — use it.
**Data-decided:** token cap ∈ {256, 512, 1024}; compared against the fixed-token baseline **at equal retrieved-token budget** (bigger chunks trivially inflate Recall@k).
*Amended by proposal 002, `docs/proposals/002-chunk-split-units.md` (approved by the owner): split units for oversized cells, the oversize flag, and the output policy.*
